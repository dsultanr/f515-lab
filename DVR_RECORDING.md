# Регистратор F515: как он работает на самом деле

Разбор `com.seres.dvr` — штатного видеорегистратора головного устройства. Всё ниже получено
декомпиляцией `/system/app/SeresDVR/SeresDVR.apk` (73 МБ, 5 dex, jadx) и сверено с
поведением живой машины.

Два вывода, которые расходятся с ожидаемым: **регистратор пишет всегда, пока голова не
спит** — никакого режима стоянки или ночи у него нет; и **чистит карту он не по возрасту
файлов, а по порядку строк в MediaStore**, из-за чего свежая запись может быть удалена
раньше трёхсуточной.

## 1. Куда пишет

```
/storage/<UUID>/SeresDVR/
├── Photo/                  снимки по кнопке/голосу
├── RecordLoop/Guest/       циклическая запись
└── RecordEmergency/Guest/  по датчику удара
```

UUID тома меняется между сессиями и переустановками карты — постоянного пути нет.

Имя файла: `<6 hex>_MP4_<YYYY>_<MMDD>_<HHMMSS>.mp4`, например `a1b2c3_MP4_2026_0101_120500.mp4`.

**Время в имени — время КОНЦА клипа, не начала.** Проверено дважды по впечатанным в кадр
часам: файл `..._120500` содержит интервал 12:04:00–12:05:00.

Префикс из шести hex-символов случаен и хронологии не несёт: сортировка по имени даёт
произвольный порядок, время лежит в четвёртом и пятом полях.

Текущий сегмент существует как `*.temp` и переименовывается в `.mp4` только при закрытии.

## 2. Что внутри

Энкодер настраивается в `media/encode/VideoEncoder.java`:

```java
MediaFormat.createVideoFormat(MIME_TYPE, w, h);
createVideoFormat.setInteger("bitrate", 4194304);    // 4 Мбит/с
createVideoFormat.setInteger("frame-rate", 25);
createVideoFormat.setInteger("i-frame-interval", 1); // опорный кадр каждую секунду
```

`BITRATE_MODE` не задан вовсе — работает умолчание вендорского энкодера, то есть **VBR с
потолком 4 Мбит/с**. Поэтому размер файла есть функция сложности сцены. Замеры на минутных
сегментах:

| размер клипа | что это |
|---|---|
| 30.2–30.4 МБ | движение: кодек упирается в потолок (4 Мбит/с × 60 с = 30 МБ) |
| 16–25 МБ | стоянка днём |
| 4.6–4.9 МБ | стоянка ночью, тёмная статичная сцена |

Разделение получается без перекрытия. Ночью **не включается** никакой пониженный режим
качества: формат тот же 1080p@25 с ключевым кадром раз в секунду, просто H.265 хорошо жмёт
тёмную статику.

В кадр впечатывается телеметрия: скорость, режим коробки, поворотники, VIN, время.

Источник кадров — одна камера DVR (`CAMERA_POSITIONS_DVR = {0}`, qcarcam input 0), 1080p,
если `ID_DVR_CAMERA_TYPE` не переключает запись на четыре камеры кругового обзора (720p).

## 3. Длительность сегмента

Не пользовательская настройка. Это бинарный выбор 30 с или 60 с из конфигурации автомобиля,
зашитый константами в `CarConfigManager`:

```java
public static boolean record1Minute() {
    return PersistenceUtil.getInstance()
        .getPersistenceValue(ConfigKeyInner.ID_DVR_RECORD_TIME, 0) == 1;
}
public static long getRecordDelayTime() { return record1Minute() ? 30000    : 15000;    } // мс
public static long getRealRecordTime()  { return record1Minute() ? 60500000 : 30500000; } // мкс
public static long getRealCacheTime()   { return record1Minute() ? 62000000 : 32000000; } // мкс
```

Период сегмента = `getRecordDelayTime() × 2`. Промежуточных значений и опции «5 минут» в
прошивке нет.

Ограничитель здесь не диск, а оперативка: сегмент целиком копится в RAM (`MediaFrameQueue`) и
сбрасывается в файл разом — 1 мин ≈ 31 МБ, 3 мин ≈ 92 МБ, 5 мин ≈ 153 МБ. Отсюда и заводской
потолок в минуту: это «держим последние N секунд в памяти и сбрасываем», а не потоковая
запись в файл.

## 4. Что решает «писать или не писать»

Единственный гейт — `DvrManager.checkOpenLoopRecord()`:

```
приложение инициализировано  &&  isRecordOpen  &&  камера жива  &&  накопитель доступен
        → startLoopRecord()
```

Ни времени суток, ни ACC, ни скорости, ни режима стоянки в этом решении нет. В
`CarConfigManager` двадцать ключей `ID_DVR_*` — сегмент, тип камеры, микрофон, водяные знаки,
блокировка клипов, приватность — и ни одного про стоянку или ночь. В `receiver/` только
загрузка, хардкнопка и голосовые команды: ни будильника, ни таймера, ни подписки на питание.

Сигнал ACC приложение читает (`onAccChange`), но использует только для водяного знака — на
решение писать он не влияет.

Отсюда следует, что регистратор — **пассажир системы питания**. Голова проснулась — он пишет,
уснула — не пишет. Наблюдаемые в архиве многочасовые непрерывные ночные серии и, наоборот,
пачки по 2–5 минут с интервалом в двадцать с лишним минут — это не режимы регистратора, а
поведение SoC.

## 5. Ротация

Реализация: `com.seres.dvr.usb.UsbManager.onCyclicCoverage()`. Вызывается из `DvrManager` в
`onRecordFinish` при `LOOP_RECORD`, то есть после каждого закрытого сегмента, плюс перед
стартом обычной записи.

### Условие

```java
long totalAvailableSize = getTotalAvailableSize();   // свободно на томе записи
double d = totalAvailableSize / 1048576.0d;
if (d <= 600.0d) { /* удаляем */ }                   // порог 600 МБ
```

### Сколько удаляет за раз

```java
if (i >= CarConfigManager.getCameraPositionLength() * 20) break;
```

При одной камере DVR это ровно 20 файлов за срабатывание — около 0.6 ГБ при минутных клипах в
движении. Наблюдение совпадает: между двумя снимками каталога с интервалом в сутки исчезло
ровно 20 файлов.

### Как выбираются жертвы

Не по файловой системе, не по имени, не по `mtime`. Запросом к MediaStore:

```java
cursor = resolver.query(MediaStore.Video.Media.EXTERNAL_CONTENT_URI,
        new String[]{_id, _data, date_added},
        "_data LIKE ?", new String[]{loopPath + "/%"},
        "date_added ASC");            // ← порядок удаления
...
resolver.delete(uri, "_id IN (...)", ids);
```

`date_added` — это когда строка появилась в базе MediaStore, а не когда снят клип. Отсюда два
следствия, оба подтверждены на живой машине:

1. **Файла нет в MediaStore — он не будет удалён никогда.** Он занимает место бессрочно, и
   полезная ёмкость карты уменьшается на его размер. Записи попадают в базу через
   `MediaScannerUtils.refreshFiles`, который `VideoManager` дёргает после закрытия каждого
   файла; если скан тогда не прошёл, клип остаётся вне учёта.
2. **Порядок удаления не совпадает с хронологией.** Наблюдался случай, когда чистильщик съел
   поездку возрастом 17 часов и не тронул несколько сотен клипов возрастом почти трое суток:
   старые файлы отсутствовали в базе, и «самым старым» для него оказался свежак.

Состояние учёта видно запросом на устройстве:

```sh
content query --uri content://media/external/video/media \
  --projection _data:date_added \
  --where "_data LIKE '%RecordLoop%'" --sort "date_added ASC"
```

Строк заметно меньше, чем файлов в каталоге, — значит часть карты для чистильщика невидима.

### Штатная блокировка от удаления

При `ID_DVR_ENABLE_LOOP_VIDEO_LOCK = 1` вместо `deleteFile` работает `deleteLockFile` — тот же
запрос, но пропускающий строки с ненулевым `is_lock`:

```java
if (i3 == 0) { /* только незаблокированные идут в список на удаление */ }
```

Колонка `is_lock` — вендорское расширение MediaStore; наличие зависит от прошивки.

### Аварийные записи

Фильтр `_data LIKE '<loopPath>/%'` покрывает только петлю. Каталог `RecordEmergency` не
чистится вообще: аварийные клипы лежат бессрочно и занимают место, которое чистильщик вернуть
не может.

При этом аварийная запись **отказывается стартовать, когда свободно ≤ 600 МБ**
(`checkAvailableSizeShowTip` → ранний выход из `runEmergencyRecord`). На заполненной карте
свободное место постоянно колеблется около этого порога, поэтому удар в неудачный момент
может не записаться.

## 6. К чему этот алгоритм привёл на исследуемом стенде

Снимок каталога петли на машине, где регистратор проработал без вмешательства несколько
месяцев. Том — 15 ГБ, занято 94%, свободно около гигабайта, то есть система постоянно
живёт у самого порога срабатывания чистильщика.

Содержимое каталога петли:

| что | файлов | объём |
|---|---|---|
| закрытые клипы `.mp4` | 711 | 12.87 ГБ |
| незакрытые `.temp` | 26 | 134 МБ |

**Больше половины карты занято одним днём, который чистильщик не трогает.** Из 711 клипов
524 (7.72 ГБ) относятся к одним суткам — непрерывная серия с ночи до вечера. За сутки
наблюдения из неё не удалилось ни одного файла, хотя это самые старые записи на карте.
Похоже, что этих файлов нет в MediaStore, и тогда они бессмертны по построению алгоритма
(см. следствие 1 в разделе 5). Проверку запросом `content query` довести не удалось — машина
ушла со связи; это единственное недоказанное звено в разборе.

**Удаляется при этом свежее.** Сравнение двух листингов с интервалом в сутки: исчезло ровно
20 файлов — 18 подряд идущих клипов вечерней поездки, которой на тот момент было 17 часов,
и два первых клипа следующей поездки. Ни одного файла возрастом почти трое суток не тронуто.
Размер пачки точно совпал с `getCameraPositionLength() * 20`.

Поездка при этом потеряна целиком: восемнадцать минут подряд, копий нигде нет.

**Незакрытые `.temp` накапливаются годами.** Двадцать шесть штук с датами за четыре
предыдущих месяца — остатки сегментов, которые не были переименованы (падение процесса,
пропажа питания). Расширение не `.mp4`, поэтому под фильтр чистильщика они не попадают
и лежат бессрочно.

**Аварийный каталог занят двумя клипами месячной давности** (61 МБ) — ожидаемо, он не
чистится вовсе.

Суммарно: из 15 ГБ карты под перезапись реально доступно **около 5–6 ГБ** — остальное
занято тем, что алгоритм вернуть не может. При 30 МБ/мин в движении это примерно **три
часа записи**, после чего начинает стираться отснятое сегодня. Разброс дат в каталоге
(от августа до сегодняшнего дня) создаёт ложное впечатление глубокого архива: фактическое
окно, в течение которого запись гарантированно жива, измеряется часами и зависит не от её
возраста, а от того, попала ли она в MediaStore.
