# Как трекер Vega и облако управляют машиной и собирают телеметрию

## Проект: Телематика Seres F515 / Evolute i-Space 4WD & трекер Vega MT X CAN

Разбор штатного контура управления и телеметрии электромобиля Evolute: как
телематический блок **Vega MT X CAN** общается с облаком **Evassist**, какими
протоколами отдаёт данные и как облачная команда из приложения доходит до
исполнения на CAN-шине автомобиля. Материал восстановлен по разбору официального
приложения Evolute / конфигуратора Vega и заводской конфигурации трекера.

Конкретные PIN-коды и IMEI в тексте намеренно опущены (заменены плейсхолдерами) —
важна механика, а не секреты конкретного блока.

---

## 1. Обзор контура

Трекер стоит на автомобиле, врезан в CAN-шину, и является **TCP-клиентом**: по
сотовой сети он сам звонит на облачные серверы Evassist. Облако хранит телеметрию
и показывает её в приложении; обратно — через облако проходят команды.

```
       Автомобиль                     Сотовая сеть             Облако Evassist                Клиент
 ┌────────────────────┐                               ┌──────────────────────────┐     ┌────────────────┐
 │ CAN-шина            │                               │ caronline / vega /        │     │ Приложение      │
 │ (шлюз кузова, БМС,   │   чтение сигналов              │ telemetry .evassist.ru    │     │ Evolute,        │
 │  климат, замки)      │◀──────────┐                   │ + client-bff-service      │◀───▶│ веб-кабинет     │
 └─────────┬───────────┘           │                   └─────────────┬────────────┘     └────────────────┘
           │ декод в параметры      │ выдача CAN TX-кадров            │
           ▼                        │ (заводские скрипты 0–7)         │
 ┌────────────────────┐             │                                │
 │ Трекер Vega MT X CAN│────────────┘   телеметрия (push / poll) ───▶ │
 │                     │◀────────────── команды (по авториз. сессии) ─│
 └────────────────────┘
```

Два независимых направления на одном блоке:
- **RX** — трекер читает сигналы CAN, декодирует в именованные параметры и шлёт их в облако (телеметрия).
- **TX** — по команде из облака трекер выдаёт на ту же шину заранее заданные CAN-кадры (управление).

---

## 2. Где стоит трекер и что он видит

Блок подключён к кузовному CAN-шлюзу автомобиля, запитан от бортсети и имеет
собственный Li-Po АКБ (чтобы пережить обесточивание). На шине он **слушает**
заранее настроенный набор сигналов (CAN-матрица в прошивке) и **декодирует** их в
параметры: заряд тяговой батареи, запас хода, напряжение 12 В, одометр,
температуры (за бортом, в салоне, батарея, ОЖ), состояние замков, дверей,
багажника, зажигания, зарядки и т.п.

Важно: трекер отдаёт наружу **только уже декодированные, настроенные параметры**,
а не сырой поток шины. Это определяет границы всего контура (см. раздел 10).

---

## 3. Серверные слоты трекера (Setting 3001)

Адреса облачных серверов хранятся в параметре `3001` — это четыре слота вида
«хост:порт + протокол». Каждый слот — отдельное исходящее соединение трекера.

| Слот | Адрес (заводской) | Протокол | Роль |
|:---:|---|---|---|
| sub0 | `caronline.evassist.ru:21123` | `0x05` Wialon Combine | Основная телеметрия (богатый push) |
| sub1 | `vega.evassist.ru:21124` | `0x03` Vega Binary | Служебный канал |
| sub2 | `caronline.evassist.ru:21124` | `0x03` Vega Binary | Vega-binary канал |
| sub3 | `telemetry.evassist.ru:21124` | `0x03` Vega Binary | Телеметрия + команды (рабочий канал) |

Трекер инициирует соединение по каждому активному слоту и держит сессию; сервер
по ней и получает телеметрию, и отправляет команды.

---

## 4. Телеметрия: машина → облако

Данные идут тремя протоколами в зависимости от слота:

- **Wialon Combine (`0x05`)** — «богатый» инициативный push: одним потоком позиция
  (время, широта/долгота, скорость, курс) **и весь набор датчиков** (заряд, замок,
  температуры, напряжение, двери и десятки CAN-параметров). Кадр: заголовок с меткой
  времени и координатами, затем TLV-список датчиков (`тег = 0x8000 | sensor_id`,
  тип задаёт ширину значения). Трекер шлёт это сам, по событию/периоду.
- **Wialon IPS (`0x02`)** — лёгкий формат позиции и отдельных параметров.
- **Vega binary (`0x03`)** — датчики **по запросу** сервера (опрос нужного ID),
  плюс пакетное чтение; по этому же каналу идут команды (раздел 5).

Типичный набор параметров: `soc` (заряд %), `range_ev` (запас хода), `battery_12v`
(В), `odometer` (км), температуры за бортом/в салоне/батареи/ОЖ, уровень GSM,
скорость, координаты, зажигание, центральный замок, двери, багажник, подключение
зарядки, активная зарядка. Push-канал (Combine) обновляет всё инициативно;
binary-канал даёт точечный опрос конкретного датчика, когда это нужно серверу.

---

## 5. Команды: облако → машина

Путь команды:

```
Приложение Evolute → client-bff-service (облачный BFF) → сервер Evassist
   → трекер (по авторизованной Vega-binary сессии) → прошивка трекера
   → исполнение заводского CAN TX-скрипта → кадры на CAN-шину → реакция авто
```

Пользователь в приложении нажимает действие; облачный BFF транслирует его в
**телематическую команду** трекеру. Прошивка сопоставляет её с запуском
соответствующего **заводского CAN TX-скрипта** по индексу слота (0–7). То есть
облако не формирует CAN-кадры — оно лишь «нажимает кнопку» предопределённого
скрипта внутри трекера, а кадры на шину выдаёт уже сам блок.

| Действие в приложении | → CAN TX-скрипт | Эффект на авто |
|---|:---:|---|
| Поставить на охрану | слот 0 «в охрану» | Запирание центрального замка |
| Снять с охраны | слот 1 «с охраны» | Отпирание центрального замка |
| Включить охлаждение | слот 2 «охлаждение» | Дистанционный запуск кондиционера |
| Климат 22 °C Auto | слот 3 «22 auto» | Преднастроенный климат 22 °C |
| Предпусковой прогрев | слот 4 «прогрев» | Прогрев салона и батареи |
| Открыть багажник | слот 5 «багажник открыть» | Открытие багажника |
| Закрыть багажник | слот 6 «багажник закрыть» | Закрытие багажника |
| Клаксон | слот 7 «гудок» | Звуковой сигнал |

На уровне протокола часть действий соответствует записи телематических настроек
(например, `1349`/`1350` — запереть/отпереть ЦЗ, `1346` — охлаждение, `1347` —
прогрев, `1348` — гудок); результат один — запуск соответствующего слота `5502`.

---

## 6. Заводские CAN TX-скрипты (Setting 5502)

Сами скрипты — восемь заводских слотов в параметре `5502`. Каждый слот — это
82-байтная структура: имя, число повторов и список CAN-кадров
(`задержка_мс`, `CAN_ID`, номер шины, 8 байт данных). По триггеру прошивка
проигрывает кадры слота на шину в нужном порядке/с задержками.

Заводской набор (по дампу памяти трекера):

| Слот | Имя | Назначение |
|:---:|---|---|
| 0 | в охрану | Запереть центральный замок (постановка на охрану) |
| 1 | с охраны | Отпереть центральный замок (снятие с охраны) |
| 2 | охлаждение | Дистанционный запуск кондиционера |
| 3 | 22 auto | Климат 22 °C Auto |
| 4 | прогрев | Предпусковой прогрев салона и батареи |
| 5 | багажник открыть | Открыть багажник |
| 6 | багажник закрыть | Закрыть багажник |
| 7 | гудок | Звуковой сигнал (клаксон) |

Эти скрипты задаются заводом (редактор CAN-матрицы — только в десктопном
конфигураторе Vega, локально); облако и приложение их не редактируют, а лишь
вызывают по индексу.

---

## 7. Авторизация канала

Без авторизации сервер не может ни опросить датчики, ни отправить команду. В стеке
Vega две независимые системы:

- **PIN трекера** (кадры `0x05` / `0x06`): при подключении слота сервер
  предъявляет PIN (ASCII-цифры с нуль-терминатором), трекер его проверяет. PIN
  **свой на каждый сервер/слот** — поэтому команда, валидная для одного канала, не
  пройдёт по другому. (Значения PIN здесь опущены.)
- **Challenge-response** (`0x22` / `0x23`): серверная авторизация с хардкод-солью в
  прошивке/приложении — защита уровнем выше.

Практический итог: управляет машиной только тот канал, который прошёл авторизацию
своим PIN; «подменить» команду в чужую сессию без этого нельзя.

---

## 8. Облачная топология Evassist

- `caronline.evassist.ru` (Combine на :21123 и Vega-binary на :21124) —
  **недоступен с 2026-10-11**.
- `vega.evassist.ru:21124` — служебный канал.
- `telemetry.evassist.ru:21124` — **живой телеметрийный канал** (слот sub3),
  фактически единственный рабочий.
- `app.evassist.ru` / `client-bff-service` — API приложения и бизнес-логика,
  которая превращает нажатие в телематическую команду.

Из этого следует зависимость: раз живым остаётся по сути один канал (`telemetry`),
то и телеметрия, и команды приложения завязаны на него — при его недоступности
приложение теряет и то, и другое, хотя сам трекер на машине продолжает читать шину.

---

## 9. Что откуда берётся в приложении

Каждый показатель на экране приложения — это декодированный CAN-параметр, прошедший
путь «шина → трекер → облако → приложение».

| Экран приложения | Параметр от трекера |
|---|---|
| Заряд, % | `soc` (CAN → декод) |
| Запас хода, км | `range_ev` |
| Напряжение 12 В | `battery_12v` |
| Пробег | `odometer` |
| Температуры (за бортом / салон / батарея / ОЖ) | соответствующие CAN-сигналы |
| Замок / двери / багажник / зажигание | бинарные CAN-сигналы |
| Положение на карте | Wialon-позиция (широта/долгота/курс/скорость) |
| Кнопки управления | обратный путь из раздела 5 |

---

## 10. Границы канала

Что контур **умеет**:
- отдавать в облако декодированную телеметрию (только те сигналы, что настроены в
  CAN-матрице прошивки);
- исполнять по команде из облака предопределённые действия — заводские CAN TX-скрипты
  (слоты 0–7) / телематические настройки (`1341–1350`).

Чего по этому каналу **нет**:
- сырого CAN-сниффинга (трекер наружу сырую шину не отдаёт — только декодированные
  параметры);
- произвольных CAN-кадров удалённо вне заводских скриптов (составление новых
  последовательностей = правка CAN-матрицы, а это локальная операция десктопного
  конфигуратора, не облачная команда).

Именно поэтому снять полный дамп шины или послать нестандартный кадр удалённо через
облако нельзя — для этого нужен физический доступ к CAN (USB-CAN адаптер / сервисный
конфигуратор у шины).

---

## 11. Локальный слой: интеграция `vega-ha` поверх штатного контура

Весь контур выше — заводской, завязанный на облако Evassist. Поверх него можно
поднять **локальный, облако-независимый слой** — интеграцию для Home Assistant
[`vega-ha`](https://github.com/dsultanr/vega-ha-integration). Идея: вклиниться в тот
же механизм серверных слотов, не меняя ни прошивку трекера, ни автомобиль.

**Как встраивается.** Один из серверных слотов трекера (`Setting 3001`)
перенаправляется с облачного адреса на хост Home Assistant. Интеграция поднимает
внутри HA **сырой TCP-слушатель** (по умолчанию порт `21443`) — ровно тот транспорт,
которого ждёт трекер (Vega binary / Wialon). Трекер, как обычно, сам звонит на этот
адрес и держит сессию. Для HA это выглядит как ещё одно отдельное устройство со своим
набором сущностей (телеметрия + кнопки), параллельно штатному облачному.

**Два режима, которые можно совмещать:**

- **Прокси-режим** — HA встаёт «посередине» слота: принимает сессию трекера и
  прозрачно передаёт её дальше в облако Evassist (`telemetry.evassist.ru`). Благодаря
  этому **официальное приложение Evolute остаётся онлайн** — для облака ничего не
  меняется. Попутно HA декодирует тот же поток и наполняет локальные сущности.
- **Direct-режим** — HA сам работает по этой уже авторизованной облаком сессии:
  опрашивает датчики и отправляет те же **предопределённые команды** — записи настроек
  `1341–1350` и запуск заводских CAN TX-скриптов (слоты 0–7, раздел 5–6). Отдельный
  PIN для этого не нужен: команды идут по сессии, которую облако уже авторизовало.

Режимы совместимы: HA может одновременно ретранслировать слот в облако (приложение
живёт) **и** читать телеметрию/слать команды локально.

**Что даёт.** Те же параметры, что уходят в облако (раздел 4), появляются как
нативные сущности HA (заряд, запас хода, температуры, замок, двери, зажигание,
позиция на карте), а те же действия (раздел 5) — как кнопки с подтверждением.
Дополнительно интеграция умеет читать/править заводские CAN-скрипты (`Setting 5502`)
из интерфейса. В итоге получается локальный канал телеметрии и управления, не
зависящий от доступности облачных эндпоинтов Evassist.

**Границы те же (раздел 10).** `vega-ha` работает поверх штатного протокола, а не в
обход него: доступны только декодированная телеметрия и предопределённые
команды-скрипты. Сырого CAN-сниффинга или произвольных кадров локальный слой не
добавляет — это по-прежнему физический доступ к шине.
