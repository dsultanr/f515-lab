# Вариант recent5: закреплённые приложения вместо реальных недавних

Виджет «Недавние приложения» на главном экране F515 (см.
[LAUNCHER_WIDGET_TWEAKS.md](LAUNCHER_WIDGET_TWEAKS.md), твик `recent5`) показывает не
реально недавние задачи, а фиксированный список из 5 приложений. Это **замена** `recent5.js`,
а не отдельный твик: оба варианта хукают один и тот же метод
`NearTaskSmartWidgetService.setIcons` в одном и том же процессе `com.seres.launcher` —
использовать вместе с обычным `recent5` нельзя (второй инжект в уже хукнутый процесс
недопустим).

Список пока захардкожен в самом агенте — механики выбора приложений в UI тулбокса нет.

## Список (в порядке слева направо)

```js
const PINNED = [
  'ru.yandex.yandexnavi',   // Яндекс Навигатор
  'ru.yandex.music',        // Яндекс Музыка
  'com.ivolk.StrelkaGPS',   // Стрелка
  'com.ispace.toolbox',     // iSpace Toolbox
  'su.dsr.f515usbwwan',     // F515 USB WWAN
];
```

Чтобы поменять — править `PINNED` в `pinned-recent5.js` (исходник в
`recon/launcher-widget-agent/`) и пересобрать (`npx frida-compile pinned-recent5.js -o
pinned5-iife.js -B iife -S`), результат кладётся в `repo-f515-widget-tweaks/agents/recent5.js`
и на голову в `/data/local/tmp/f515widgets/recent5.js`.

## Откуда брать AppInfoModel для закреплённых пакетов

Не через `PackageManager` руками — есть готовая БД лаунчера:

```java
DataBaseManager.INSTANCE.getAppListDataBase().getAppDao().getByName(packageName)
// -> AppInfoModel(id, packageName, activityName, iconRes, label, ...)
```

Та же таблица, что и обычный каталог приложений лаунчера (`AppListBusiness` её наполняет
сканом всех установленных пакетов) — значит иконка/лейбл/activityName гарантированно
совпадают со штатными, и клик по плитке (через `setTag` + резолвер в
`NearTaskSmartWidgetService.setListener`) открывает то же самое приложение, что и обычный
ярлык.

## Грабли №1: `AppListDataBase` нельзя трогать с главного потока

`AppListDataBase` собрана **без** `allowMainThreadQueries()` (в отличие от
`PersonalSetDatabase` у другого компонента прошивки, где этот флаг стоит явно). `setIcons`
выполняется на `Dispatchers.Main` (диспетчер `C00691` в `createView$1$1` явно берёт
`kotlinx.coroutines.internal.l` — Main.immediate). Синхронный `getByName()` прямо внутри
хука `setIcons` падает:

```
IllegalStateException: Cannot access database on the main thread since it may potentially
lock the UI for a long period of time.
```

Проверено на устройстве 16.08.2026 отдельным диагностическим агентом (`room-test`):
вызов того же `getByName()` в фоновом `java.lang.Thread` отрабатывает нормально и
возвращает реальные `label`/`iconRes`/`activityName`/`process`; тот же вызов через
`Java.scheduleOnMainThread` — падает с приведённым выше исключением.

**Решение:** резолвить весь `PINNED` список ОДИН РАЗ в фоновом `java.lang.Thread` сразу
после инжекта, кешировать готовые `AppInfoModel`; сам хук `setIcons` только читает кеш,
к Room не обращается вообще.

## Грабли №2: источник данных виджета не привязан к живым переключениям задач

Ожидаемая модель («открыл приложение → недавние обновились») тут не работает.
`SmartFlow.d` (`nearTaskerStateFlow`, `com.seres.launcher.assembly.SmartFlow`) — источник
данных для этого виджета — на практике уже полон записей сразу при старте лаунчера
(проверено: 19 приложений, включая давно не открывавшиеся системные) и на протяжении
многих `am start <pkg>; input keyevent HOME` в ходе тестирования **не менялся ни разу**.
Отдельный трекер задач `NearTaskStateFlow` (`TaskStackListener`, `onTaskFocusChanged` и
т.д.) существует в том же дексе, но используется только полноэкранным `RecentActivity»
(«все недавние»), а не этим доковым виджетом — прямой связи между ними в декомпилированном
коде нет. Кто именно и когда пишет в `SmartFlow.d`, не найдено (не появляется в тексте
декомпила ни разу вне самого объявления поля) — вероятно, наполняется один раз при
старте лаунчера через код, который jadx не смог связать текстовым поиском.

Следствие: `setIcons` может не вызываться повторно **очень долго** после того, как виджет
один раз отрисовался при старте лаунчера. Ждать штатного вызова, чтобы применить
`PINNED`, ненадёжно.

**Решение:** сразу после резолва `PINNED` агент **сам** форсирует перерисовку — находит
живой экземпляр `NearTaskSmartWidgetService` через heap walk (`Java.choose`) и вызывает
`instance.setIcons(new ArrayList(), instance.getBinding())` вручную, не дожидаясь потока.
Повторяет попытку каждые 500 мс до 15 секунд (объект мог ещё не существовать в момент
инжекта).

## Заметка про тайминг форс-рендера: ручной тест vs реальный перезапуск

При ручном тестировании 16.08.2026 (`kill` процесса лаунчера + `frida-inject` из отдельных
adb-команд, с задержками в несколько секунд между ними) `Java.choose('...NearTaskSmartWidgetService')`
стабильно находил **0 живых экземпляров**, даже находясь ровно на главном экране без
посторонних активити на переднем плане. Похоже, что Java-объект сервиса — короткоживущая
«фабрика View»: `createView()` отрабатывает почти мгновенно при старте процесса, и в
искусственных условиях ручного теста (несколько секунд между `kill` и инжектом через
отдельные adb-вызовы) агент стабильно опаздывал.

**Проверено на реальном перезапуске головы (ребут 16.08.2026, 19:33):** `widgets-apply.sh`
вызван сразу после `sys.boot_completed=1`, без ручных пауз — heap walk нашёл живой экземпляр
и применил список **с первой попытки**:

```
resolved 5 of 5 pinned apps
slots: 5
filled 5 of 5 (pinned)
force-render[1]: применено к живому экземпляру
```

На экране — ровно 5 закреплённых плиток в заданном порядке (Навигатор, Я.Музыка, Стрелка,
iSpace ToolBox, F515 USB WWAN), иконки и подписи корректные. Значит опоздание было
особенностью именно ручного теста (задержки между отдельными adb-командами), а не самого
подхода — продовый путь применения (`widgets-apply.sh`, вызванный сразу по обнаружению pid)
успевает без проблем.

**Безопасность это не задевает в любом случае:** любая ошибка в хуке (включая «объект не
нашёлся») просто оставляет штатное поведение — реальные недавние в 3 плитки, как до твика.
Худший случай не меняется относительно обычного `recent5`.

## Развёртывание (16.08.2026)

```sh
# сборка
cd recon/launcher-widget-agent
npx frida-compile pinned-recent5.js -o pinned5-iife.js -B iife -S

# в репозиторий твиков — становится новым содержимым recent5.js
cp pinned5-iife.js ../../repo-f515-widget-tweaks/agents/recent5.js

# на голову — тот же путь, что использует widgets-apply.sh
adb push repo-f515-widget-tweaks/agents/recent5.js /data/local/tmp/f515widgets/recent5.js
adb shell sh /data/local/tmp/f515widgets/widgets-apply.sh   # переинжект по несовпадению pid
adb shell sh /data/local/tmp/f515widgets/widgets-watch.sh &  # сторож дальше сам следит
```

Применено и проверено на устройстве: `recent5-live=1`, резолв всех 5 пакетов подтверждён
логом (`/data/local/tmp/launcher-widget-unlock.log`, тег `[pinned5]`), визуально подтверждено
скриншотом после реального ребута головы 16.08.2026 19:33 — 5 закреплённых плиток на месте.

Автозапуск сторожа после ребута (заявлен в README тулбокса) не сработал при этом ребуте —
`watchdog=0` сразу после загрузки, поднят вручную (`sh widgets-watch.sh &`). Не разбиралось
подробно; вероятная причина — Android держит только что установленный/давно не открывавшийся
пакет в «stopped state» и не доставляет ему `BOOT_COMPLETED`, пока его не запустят вручную
хотя бы раз.
